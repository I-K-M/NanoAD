# N09a — NanoState durable transaction core

Status: experimental implementation slice; native execution and qualification remain pending. Parent: [N09](../../tickets/001-nanoad/N09-state-recovery.md).

## State and journal

A single append-only state.log is the authoritative state and write-ahead journal. Each bounded JSON record carries schema version, strictly increasing revision, previous SHA-256 and a typed event. The frame adds the SHA-256 of the payload. Replay validates the complete chain and semantic transitions. There is no separate mutable state file or ledger that could disagree with the journal. A complete validated frame is the logical atomic state transition. Flush the journal file before returning success; a partial write, uncertain flush or changed length poisons the open Store. A torn/invalid tail blocks replay; do not truncate it, silently fall back to a prefix or initialise a replacement. A complete frame after an ambiguous write may represent a committed transition: reopen and reconcile, never blindly retry. SHA-256 detects accidental corruption, not a hostile writer or deliberate deletion of a valid suffix.

Initialisation requires a new stable lock file and a new journal; existing/missing/partial state is never silently recreated. The local OS file lock is exclusive and non-blocking for the lifetime of the Store; never unlink it, use stale PID heuristics or take over a held lock. The test harness launches separate processes to check exclusion and release after process exit. File sync is required at each append; Linux also syncs the directory after initial creation. Windows directory-entry durability, sudden power loss and device-cache behaviour are not qualified. A real execution path must establish a trusted fixed local directory, restrictive ACLs, no aliases/reparse points, exclusive provider ownership and a storage durability contract. Cooperative locking is not protection against a hostile administrator or direct VirtualBox changes.

Limits: 32 guests, 32 KiB JSON payload, 8 MiB journal, 4096 records; reserve space for intent, dispatch and completion before new intent. No auto-rotation or deletion. Export/compaction of journal history is a later reviewed operation; a full or damaged journal requires manual recovery. The bounded replay buffer does not load the entire journal into RAM.

## Ownership and resource reservation

Initial records contain canonical lab/guest/VM UUIDs, overlay and base medium UUIDs, canonical base SHA-256, and qualified numerical upper bounds. Initialisation assumes the full independently verified inventory is stopped; this API is not an adoption workflow or a CLI command. Reject aliasing, inconsistent shared base identity, duplicate guest/VM/overlay IDs and invalid cost envelopes. No arbitrary paths, credentials or mutable costs in event payloads. A pending or stopping workload is charged its peak; active retains its steady envelope. A stopped VM retains its disk records. Reconstruct the NanoRAM ledger from replay; no cached desired state, failed observation, or interrupted operation releases it.

## Transaction order

1. Obtain exclusive Store, read the journal and reconcile the full provider/media inventory with fresh observations and independently qualified scope. Approval is an internal explicit precondition; N11/N12 must bind it to an exact plan hash.
2. Begin start: validate target ownership, stopped state, isolation and release evidence, run NanoRAM/NanoDisk admission and append+sync intent containing the pending reservation. Begin stop: validate an owned running VM, append+sync intent; retain peak reservation.
3. Recheck ownership, freshness and admission immediately before start; append+sync the dispatch barrier. No actual mutation is wired in this slice. Once dispatch exists, the action MAY have executed, including after process crash. Reopen must never redispatch.
4. Complete only with fresh verified target state: start requires running, native readiness, isolation and scratch accounting; stop requires powered off, independently verified resource release and scratch accounting. A stopped observation alone is insufficient. Record completion and new state in one synced event.
5. An undispatched intent can be cancelled explicitly with fresh prior-state and release/health evidence. After dispatch, do not cancel, force-stop, delete or reset; the explicit completion path may confirm an observed successful result after restart. Otherwise retain reservations and report manual recovery. No automatic compensation for ambiguous or irreversible changes.

The read-only reconciliation function uses the existing Adapter.observe contract (matching provider markers and VM UUID). It reports matches, drift, unavailable observations and interrupted work, and never claims a complete inventory. It does not discover foreign peers, prove media attachments, infer process credit or attest native readiness. Current native transport remains read-only; there is no production mutation path. Trusted evidence flags in the coordinator are placeholders for the future real reconciler, not user-controlled switches. All real provider operations must use the same Store lock through the action and final commit. Only one in-flight transaction per lab; a later host-wide lock is needed for competing labs sharing the same host resources.

## Checks

Run pinned Zig 0.14.1: zig fmt --check build.zig src; zig build test; zig build -Doptimize=ReleaseSafe. Tests cover replay, journal corruption, stale revision, invalid ownership, reservations retained across reopen, competing lock processes, host drift, explicit cancellation, refusal of redispatch, and verified completion/release. They exercise real local files and child-process locks, not a real VirtualBox VM.

To qualify N09, verify actual storage/ACL/lock semantics on the target NTFS host; fault-inject real process interruption and power-loss durability at each stage; reconcile actual VBoxManage markers, attachment/base identities, other VMs, resource release and native guest health; exercise end-to-end operations with independent review. No orphan deletion, snapshot restoration or automatic recovery mutation is introduced. Rollback: revert source commits; retain journal and VM evidence. No automatic on-disk schema migration.
